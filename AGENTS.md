# AGENTS.md — Danmo Make

Operational guide. User overview: [README.md](README.md).

The Python backend, MLX engine, PyInstaller sidecar, and Python CLIs are gone. The server is the Rust binary `danqing-api`.

## Naming

Product / UI / release artifacts: **Danmo Make** / `danmo-make-*`. Runtime identifiers stay `danqing-*` (binary `danqing-api`, bundle id `com.danqing.studio.desktop`, env `DANQING_*`).

## Rust MLX-C migration (P0)

The migration plan, capability matrix, and shared-component inventory live in `docs/rust_mlx_migration_plan.md`, `docs/rust_mlx_migration_matrix.json`, and `docs/rust_mlx_shared_asset_inventory.md`. Keep their statuses and evidence current.

Production families still use ggml during P0. `danmo-mlx-sys` pins `mlx-c` v0.8.0 and MLX v0.32.4 through local submodules; fmt 12.1.0 and nlohmann-json 3.11.3 are vendored with source hashes. It is the only raw MLX-C FFI crate. `danmo-mlx` owns the safe RAII wrapper; `Array`, `Device`, and `Stream` are thread-affine, and `Executor` owns a long-lived MLX thread that accepts plain-data jobs. Engine/family/common code must not import `danmo-mlx-sys`. Metal and CUDA are separate build features and separate artifacts. No production family is considered migrated until its model/version/action matrix entries pass parity, performance, and E2E on both backends.

`danmo-engine` exposes opt-in `mlx`, `mlx-metal`, and `mlx-cuda` features without changing the production ggml driver. The new `families/z_image/mlx` module covers published config, safetensors remap, shared Qwen3 tokenization, component primitives, full DiT/Euler denoise, and real-weight create slices through `common::vae::mlx` decode and RGB/PNG. Shared `weights/mlx.rs::WeightDtype` keeps every dense checkpoint tensor at its native BF16/FP16/F32 dtype in production; F32 widening is test-only for main-parity fixtures. The official Z-Image DiT is F32 (521 tensors, 24,619,634,944 bytes), while its VAE/Qwen3 are BF16; the registry's `fp16` label is not a tensor-dtype guarantee. Affine uint32 codes + scales + biases stay packed in the opaque `LinearWeight` and run through QMM without a dequantized resident copy; registry/shard quantization metadata is validated and the architecture guard prevents bypassing `LinearWeight`. Image/text padding reads checkpoint `x_pad_token`/`cap_pad_token`, `x_embedder` output returns to latent BF16, RoPE and timestep frequency/trigonometric math uses MLX operators rather than host math, and Euler casts velocity/dt back to latent BF16. RoPE tables are reused per token geometry, precomputed and explicitly evaluated outside compiled closures; no global or thread-local family cache is allowed. On pinned MLX 0.32.4 shapeless compile fails loud (`Split`/`Slice` lack `output_shapes`), so `CompiledForward` uses shape-specialized compile with only latent + timestep embedding traced. F32 main-parity slices now pass 16x16 fixed-injection/seed-42, full 1024x1024 8-step recurrence, and 768x1280 9-step no-TeaCache eager and explicit-compile paths: velocities and recurrent latents are bit-exact with main, and VAE/RGB gates pass without relaxed thresholds. Checkpoint-Native 16x16 and 768x1280 slices also pass with bit-exact latents, VAE, and RGB; Native Metal peak memory is 26.15GB versus main's 31.79GB (82.25%). `families/z_image/mlx/step_cache.rs` implements the default TeaCache gate and residual reuse; the default 9-step run and an explicit 3-compute/6-skip fixture both match main exactly. The Native production optimization is `CaptionCache` (caption branch precomputed once per run, main's `before_denoise` boundary) plus `CompiledCompute` (the 30 unified blocks + final layer under `mx.compile`, gate/residual/caption precompute stay eager); compiled TeaCache is bit-exact with the eager cached path on both fixtures. The formal warm performance gate passed on Metal (release, 768x1280 9-step default TeaCache, 5 resident passes, every pass bit-exact with main): warm p50 denoise 63.5%, encode 96.8%, VAE 85.0%, total 63.9% of main; steady resident memory after `clear_cache` is 99.3% of main. Performance must be measured with main/Rust adjacent in the same thermal window (M5 Max sustained-load throttling drifts both sides up to 2x) and parity readbacks outside the timed phases. `danmo-mlx` adds `MultiClosure` (multi-output compile), `Array::eval_all`, `Array::to_raw_bytes`, and `clear_cache`. Host-reference F32 micro probes need `MLX_ENABLE_TF32=0` on NAX chips. Published-quant checkpoint E2E, session lifecycle, production routing, and CUDA remain pending. Keep the implementation inside the existing family and reuse `common::qwen3` rather than adding a parallel tokenizer tree.

## Weights

The DiT is GGUF. The text encoder and VAE are GGUF or the published safetensors. MLX `fp16` / `int8` / `int4` / `mlx-q4` / `mlx-q8` directories are not scanned, converted, or loaded. FLUX.2 Klein 4B and Z-Image installs copy the ModelScope text encoder, VAE, and tokenizer into that version's own directory. A directory that already contains a GGUF is not treated as an old MLX pack because of the safetensors companions. An install that lists `components` writes `bundle.manifest.json` into that directory after the last file lands. `quant` is the version key. `transformer` is the planned GGUF. `text_encoder` and `vae` are the planned weight files under those directories. LTX installs add four more roles: `audio_vae`, `connectors`, `upscaler`, and `transformer_stage2` (the distilled stage-2 DiT used by the two-stage pipeline), each under its own directory and manifest slot, validated by `assert_ltx_bundle`.

- Bundle directory: GGUF DiT, GGUF or safetensors text encoder and VAE, `tokenizer.json`, `bundle.manifest.json`. Large towers may be sharded and are mmap'd per file. Duplicate tensor names across shards fail. A safetensors text encoder whose first key is `model.embed_tokens.weight` is read with that prefix on every lookup. `blk.*` names fail. Upscale bundles (SeedVR2) drop the tokenizer and text encoder: DiT GGUF plus VAE safetensors only, validated by `assert_upscale_bundle`. The fixed positive text embedding is `pos_emb.safetensors` — a bundle-local copy (root or `data/`) wins, otherwise the packaged default under `families/seedvr2/data/`.
- The SeedVR2 VAE safetensors stores 5D PyTorch conv3d kernels `[OC, IC, KD, KH, KW]`; the reader folds them to the ggml `[KW, KH, KD, IC*OC]` view without a repack. GGUF tensors past four dims (the Wan `patch_embedding.weight` conv) fold the same way: the engine parses the GGUF header itself because the ggml gguf reader refuses them. The SeedVR2 DiT GGUF keeps vectors, biases, and embeddings in F16; they are widened to F32 on load while matmuls stay Q8_0. Its VAE spec (`block_out`, resnet counts, latent channels, temporal up/down, group-norm groups) is inferred from the weight names and shapes, never from a registry flag.
- Version keys: `bf16`, `q8_0`, `q4_k`. The API drops every other key. Published VAE tensors are BF16 safetensors and are widened to F32 for the decoder graph. Inside a quantized DiT, norm scales stay F32. Matmul accepts F32, F16, BF16, Q8_0, and Q4_K.
- `load` mmaps by tensor name. The name in the file is the graph parameter name. There is no `remap_*` and no `sanitize()`. Flux2 reads the published fused names (`double_blocks`, `single_blocks`, `img_in`, `txt_in`, `time_in`, `final_layer`). Z-Image reads the published names already in its weight table. A missing tensor or a shape mismatch fails the task.
- LoRA is GGUF. The matrix name is the base parameter plus `.lora_a` or `.lora_b`. Other suffixes are not rewritten.
- Do not invent Hugging Face repo ids. Until a GGUF is published, that version key is absent and generation fails loud.

`Q8_0` is about half the F16 weight bytes. `Q4_K` is about 30%. Activations do not shrink.

## Engine rules

Long form: [docs/engine_architecture.md](docs/engine_architecture.md).

- Fail loud. No filled-in weights, no truncated prompt, no second CPU backend for an operator the chosen device cannot run. CPU as `DANQING_GGML_BACKEND` is a real device. Invalid configured backends fail startup; only an unset backend defaults to CPU.
- Engine creates one `GgmlContext` per task and injects it into every family session. Text encoders, companion LMs, DiT, FSQ, and VAE do not open another device. Families add models. A new chip backend is a `GgmlContext` backend, not a family.
- Families are isolated. A family does not import another family. `families/mod.rs` is the only match on a family id. `pipeline`, `session`, `common`, and `runtime` do not branch on family ids or contain family implementation types.
- Shared modules (`common/qwen3`, `common/vae`, `common/png`, `common/ops`, `runtime`) do not know family ids. Callers pass layer indices, a thinking flag, or a `VaeSpec`. Weight-file names such as `layers.*` and `decoder.*` are the file format.
- A difference that needs many callbacks or mode switches stays in the family. Denoise does: Flux2 steps `x + dt * (u + g * (c - u))` on `[channels, seq]`; Z-Image steps `x + dt * (c + g * (c - u))` on `[W, H, C]`.
- Schedules live in `common/ops`. Flux2's two flow-match names use empirical mu, and the timestep is cosine then sine of `sigma * 1000`. Z-Image treats `flow_match_euler_discrete` as the same scheduler: static shift unless `use_empirical_mu` is set. `linear` keeps the resolution shift.
- Standard DiT phases stay resolve → load → encode → schedule → infer → decode → persist. Job and GenerationFacade shapes use their documented shared phase order. One cgraph is reserved and replayed per denoise session.
- Server integrates through `ResolvePort`, `ArtifactSink`, and `RunObserver`. Generic `Artifact` / `EngineResult` types carry PNG, WAV, sidecars, metadata, and timings; family outputs do not leak into pipeline or server types.
- ggml calls stay in `danmo-ggml-sys` and `danmo-engine` runtime / weight code.

Every other family/action fails with `GraphNotBuilt` before queueing or when called directly. `real-esrgan-x4plus` stays in that bucket on purpose: no GGUF is published, its registry `versions` is empty, and both the HTTP gate (`ensure_available`) and the legacy `upscale` path fail loud. `z-image-turbo-fun-controlnet-union` likewise keeps an empty `versions` until an official GGUF is published; the structural-guide HTTP gate validates the guide (z_image family only, category `controlnets`, canny/depth/pose/hed/mlsd/scribble/gray/auto types, weight 0–2, paired inpaint source/mask) and resolution of the unpublished adapter fails loud. `diffrhythm-v2` has no published GGUF either (upstream ships safetensors only) and stays `GraphNotBuilt` like `real-esrgan-x4plus`. The assistant routes (`GET /v1/llm/model`, `GET /v1/vision/model`, `POST /api/chat/enhance-prompt`, `POST /v1/chat/completions`) read `llm_inference_*` settings: with `llm_inference_provider=openai_compatible` plus a configured base URL and API key they proxy the configured cloud model (non-stream JSON and streaming SSE passthrough, 502 on remote failure); every other configuration answers 503 fail loud — builtin local LLM inference is not built.
- Immutable mmap weights use the single-slot LRU + TTL cache in `weights/cache.rs`. Qwen3 embeddings use the independent four-entry cache in `common/conditioning.rs`; both are invalidated by path/length/mtime revisions. Mutable denoise sessions and per-run state are never shared.
- `runtime/capacity.rs` reports actual gallocr graph bytes, cached weights, conditioning bytes, and device memory. The first Metal task runs `runtime/probe.rs`, comparing flash attention against an independent host reference and logging timing. Small head dimensions are zero-padded to 64 and sliced back on the same device; unsupported paths fail rather than moving to CPU.

## Backend selection

`DANQING_GGML_BACKEND=auto|cpu|cuda|vulkan|metal`. The binary must be built with the matching cargo feature (`cuda`, `vulkan`, `metal`). A missing feature fails at startup or context init. `auto` is the default: startup tries only compiled backends, macOS orders Metal → CUDA → Vulkan → CPU, other platforms order CUDA → Vulkan → Metal → CPU, and each candidate must pass the attention probe. CPU remains the last fallback; selection never changes during a task. Health returns the selected backend, selection reason, and probe summary. The System Info UI displays them, and all task logs carry a `[backend]` prefix. `scripts/build_ggml_sidecar.sh` enables Metal on macOS, CUDA when `nvcc` or `CUDA_PATH` is present, and Vulkan when the SDK is present.
